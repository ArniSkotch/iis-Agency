## Две метрики поиска

Это два разных числа, а не одно, измеренное дважды. `hit-rate@5` считается механической сверкой имени файла, `Context Precision` — оценкой судьи. Различаются и знаменатели: `hit-rate@5` — по вопросам с непустым `expected_sources`, `Context Precision` — по in-scope вопросам без сбоев разбора.

| Метрика | Значение | Как получена | На каком подмножестве | С какой практики |
| --- | --- | --- | --- | --- |
| `hit-rate@5` | `<ЗАПОЛНИТЬ>` (`<N>` из `<M>` in-scope) | механическая сверка поля `source`, `python ingest.py --eval` | только вопросы с непустым `expected_sources` (13 in-scope) | П2 |
| `Context Precision` | `<ЗАПОЛНИТЬ>` | оценка LLM-судьёй, `python test_suite.py` | только in-scope вопросы, без сбоев разбора (`n` — см. «Средние») | П6 |

Знаменатель `hit-rate@5` указан явно: `out_of_scope` в замер не входит, поэтому число читается как «`<N>` из `<M>`», а не «из 16».

`out_of_scope` из обеих метрик исключён: у него нет ожидаемого источника и нет фрагментов, к которым можно предъявить «отношение к вопросу». Корректность отказа на таких вопросах проверяется отдельно (см. «Средние»).

Разница на практике: `hit-rate@5` засчитывает вопрос, если хотя бы один из пяти фрагментов взят из нужного файла, а `Context Precision` оценивает, сколько из пяти фрагментов действительно относятся к вопросу. `<ЗАПОЛНИТЬ: одна фраза о том, как эти два числа различаются на ваших данных>`.

## Как чанки попадают к судье

Судья получает на вход фактические фрагменты, ушедшие в модель, а не только эталон. Маршрут:

1. `run()` в `test_suite.py` вызывает `orchestrator.handle(session_id, question)`. Для каждого вопроса создаётся отдельная сессия `test:<uuid>`, поэтому память предыдущего вопроса ответ не искажает.
2. После `handle()` `run()` забирает `orchestrator._context[session_id]` — это те же фрагменты, что `build_messages()` передал в LLM для этого ответа.
3. `run()` передаёт их в `judge(..., chunks, case_type)`.
4. В `judge()` фрагменты вставляются в промпт через `format_chunks()`, то есть в том же формате, который видит генератор: файл, страница (если есть), близость и текст.

Пример формата, в котором судья видит фрагмент (из прогона диалога П5):

```
[garant_potrebitel_rf.pdf, стр. 35] (близость 0.8439)
и принятия в случае их подтверждения мер по п…
```

Судья видит источник и страницу каждого фрагмента, поэтому может проверить и ссылки в ответе (Faithfulness), и относимость каждого фрагмента к вопросу (Context Precision). `<ЗАПОЛНИТЬ: вставьте один реальный фрагмент из прогона test_suite.py, если нужен пример по вопросу из набора>`.

## Веб-интерфейс

`app.py` вызывает только `handle()`: в нём нет ни поиска, ни промптов, ни проверок ввода. Проверено вручную (`streamlit run app.py`):

- история диалога отображается и не теряется при отправке следующего вопроса: `<ЗАПОЛНИТЬ: да/нет>`;
- две вкладки браузера дают две независимые сессии: идентификаторы в боковой панели различаются, вопрос из одной вкладки во второй не виден: `<ЗАПОЛНИТЬ: да/нет>`;
- после кнопки «Очистить сессию» вопрос, опирающийся на прошлый ответ, система не понимает: `<ЗАПОЛНИТЬ: да/нет>`.

## Ограничения метода

Судья — `<ЗАПОЛНИТЬ: модель>`, температура `0`. Генератор — `<ЗАПОЛНИТЬ: модель>`. `<ЗАПОЛНИТЬ: если модели совпадают, оставьте следующее предложение>` Модель та же, что генерировала ответы, поэтому оценка не является независимой: модель оценивает собственную работу. Это ограничение отмечено здесь, а не замалчивается.

Языковая модель ошибается и склонна завышать оценки. Оценка судьи — инструмент отслеживания изменений между правками, а не приговор качеству системы.
